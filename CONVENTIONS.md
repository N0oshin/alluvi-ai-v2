# Code conventions

The one page to read before adding code. The shape is a **modular monolith**:
one deployable app, split into modules that own their own tables and talk to
each other only through a small public API. That keeps the option of pulling a
module out into its own service later without a rewrite.

## Layout

```
src/
  app.ts              builds the Fastify app, mounts every module
  server.ts           API process entry point
  worker.ts           job runner process entry point
  config/             environment settings (zod-validated)
  db/
    index.ts          the Drizzle client (`db`) and the pool
    schema.ts         re-exports every module's schema.ts, for Drizzle and migrations
    migrations/       generated by drizzle-kit, never edited by hand
  shared/
    http/             auth, errors, error handler, validation, idempotency,
                      rate limiting, pagination, logging, request id, time zone
    auth/             access, refresh, guest and identity tokens; signing keys
    schema.ts         enums and column helpers used by more than one module
    infrastructure/   idempotency keys, rate limit counters, outbox, audit log
                      (schema.ts plus one file per table)
  providers/          external services (email, push, storage, vision, Apple and
                      Google token verification), each with a real and a fake
                      implementation chosen by config
  jobs/
    queue.ts          the JobQueue type and the in-memory queue for tests
    runner.ts         pg-boss wiring
    definitions.ts    every job name and its payload type
    schedules.ts      cron schedules
    handlers.ts       the two infrastructure jobs, and the map that assembles
                      every module's jobs.ts for the runner
  modules/
    <name>/           one folder per bounded context, see below
test/
  db.ts               test database helpers (migrate, truncate, close)
  factories/          row builders for tests
```

## A module

Every module has the same files, in this order of dependency:

| File         | Contains                                                                                | May import                                                        |
| ------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `schema.ts`  | the module's Drizzle tables                                                             | `shared/schema`, other modules' `schema.ts` only for foreign keys |
| `queries.ts` | every database call the module makes, as plain functions                                | `db`, own `schema.ts`, `shared/*`                                 |
| `rules.ts`   | pure logic: no database, no HTTP (optional)                                             | types only                                                        |
| `routes.ts`  | Fastify routes: validate, call queries/rules, respond                                   | own files, `shared/*`, `providers`, `jobs/queue`                  |
| `jobs.ts`    | background job handlers (optional)                                                      | own files, `shared/*`, `providers`                                |
| `index.ts`   | the module's public API: `routes`, `jobs`, and the few functions other modules may call | own files                                                         |

Rules:

1. **Same names everywhere.** Do not invent new file names inside a module. If a
   module needs a second logic file (for example `plan-calculator.ts`), it is
   pure logic like `rules.ts` and is listed in the module's `index.ts` comment.
2. **A module never imports another module's internals.** It imports the other
   module's `index.ts` and nothing else. The ESLint `no-restricted-imports` rule
   enforces this.
3. **A module owns its tables.** Only its own `queries.ts` reads or writes them.
   If another module needs that data, it calls a function exported from `index.ts`.
4. **Queries are plain async functions** that import `db` directly. No store
   interfaces, no classes, no in-memory fakes. A query that must run inside a
   transaction takes an optional `tx` as its last argument.
5. **Routes take no dependencies object.** They import what they need. The only
   things passed in from `app.ts` are the providers and the job queue, because
   those differ between real and test runs.
6. **No barrel re-exports except `index.ts`.** Import from the file that defines
   the thing.

## Tests

Tests sit next to the file they test as `*.test.ts`. We test what can go wrong
in a way that costs users something, not every line:

- pure logic (`rules.ts`, `plan-calculator.ts`, `sign-in.ts`, token code)
- the job runner and queue
- one `routes.test.ts` per module covering the main happy path and the main
  failure of each endpoint, against the test database
- a query only when it has a transaction or an upsert worth proving

Database tests use `test/db.ts`: `beforeAll(migrateTestDatabase)`,
`beforeEach(truncateAll)`, `afterAll(closeTestDatabase)`. `src/db/index.ts`
connects to `TEST_DATABASE_URL` when `NODE_ENV=test`, so routes under test hit
the test database without any wiring.

## Style

- Comments explain _why_, briefly. Reference a doc section or decision number
  when one exists; do not restate the code.
- Errors are thrown as `AppError` from `shared/http/errors.ts`; the error
  handler turns them into the response envelope.
- API bodies are snake_case, code is camelCase. Convert at the route boundary.
- Phase labels and "added in Phase N" notes are not written into code
  comments; git history has that.

## Adding a feature, step by step

1. Create `src/modules/<name>/` with `schema.ts`, add its export to
   `src/db/schema.ts`, run `npm run migrate:generate`, review the SQL, run
   `npm run migrate`.
2. Write `queries.ts`, then `rules.ts` if there is logic worth isolating.
3. Write `routes.ts` and register the module in `app.ts`.
4. If it needs background work, add the job to `jobs/definitions.ts`, write
   `jobs.ts`, register it in `jobs/handlers.ts`.
5. Add `routes.test.ts` and tests for any pure logic. Update `docs/api-listing.md`.
